# Java 工程化

本章技术基线：Starsector `0.98.5a-RC7` 与 Java 17。

---

前五章涉及的代码都可以直接留在数据目录里，由游戏启动时自带的内置脚本编译器现场编译运行。这种做法省去了配置开发工具的麻烦，但游戏内置编译器只支持残缺的 Java 语法特性，报错要等到启动进游戏后才会暴露，主流编辑器也几乎无法提供补全与类型检查。代码量少时还能勉强应付，一旦进入真正复杂的系统开发，这套工作流立刻就会成为效率与排错上的双重阻碍。

## 告别内置编译器，接管真正工程

从这一章开始，教程不再把源码留给游戏现场编译，而是迁入独立的 JDK 与 Gradle 工程，在外部编译打包成可分发产物再交由游戏加载。迈过这道门槛，才算正式踏进总序里所说 "之后大概就是地狱" 的工程深水区。

**从本章开始，教程假定您已掌握基础 Java 知识。** 类、接口、继承、集合、泛型与异常处理，此后都会作为默认工具直接使用，不再专门停下来解释语法概念。如果对这些语言基础还不熟悉，强行照搬复杂架构只会变成逐行看不懂报错的苦差：**最划算的做法是先停下几天找一套基础 Java 语法教程跑顺面向对象与集合，再回到本章继续往下推进**。往后真正的难点几乎全在 Starsector 如何古怪地组织它的对象关系、生命周期与状态边界，语言语法反而是最容易跨越的部分。

## 工程纪律：配置跟仓库走，源码彻底迁出

跨出工程化这一步之后，有两条纪律必须在动手一开始就守死，并与日常协作对齐：

- **源码迁移是彻底移动，而不是留着副本复制**：如果旧目录里还留着同名源码，游戏启动时仍会用内置编译器重新编译一遍，从而与打包进去的二进制类发生同名冲突，导致报错甚至运行到旧代码。迁完后顺手清查一遍旧脚本目录、确认只剩资源配置与数据包，才能算迁移完成。
- **构建配置跟工程走，本机路径差异抽进独立文件**：依赖库版本、JDK 目标与核心游戏包的排除规则都应当写进随仓库分发的标准构建配置里，**绝不要把游戏本体的类一并打包进产物**；而不同电脑之间各自不同的游戏安装目录路径，则统一抽进被版本控制忽略的本机私有属性文件里各自填写，确保源码库无论拷到哪台机器上都能直接按相同口径构建出一致的 JAR。
