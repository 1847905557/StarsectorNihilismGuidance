# 着色器与渲染

本章技术基线：Starsector `0.98.5a-RC3` 与 Java 17；前置依赖：BoxUtil `1.5.5`。

---

直到全书末尾，绝大多数战斗表现其实依然可以在原版贴图与粒子接口里稳妥完成。但原版接口本身建立在固定管线封装之上：一旦您需要无论镜头如何缩放都保持稳定像素宽度的矢量轮廓、丝滑的抗锯齿几何边界，或者让成百上千个战场标记通过一次显卡提交批量绘制出来，Java 侧逐项绘制的精度限制与 CPU 到 GPU 反复递送数据的开销瓶颈就会迅速暴露。

## 绝大多数 MOD 根本用不到着色器

跨出这一步之前，先把最现实的技术尺度摆正：**绝大多数 MOD 根本用不到着色器，原版朴素的贴图与粒子体系足够撑完一整部完成度极高的作品。** 引入自定义着色器、显存缓冲与底层绘制管线，并不会自动让作品显得高级，反而会立刻把工程复杂度、排查难度以及面对玩家各色老旧显卡驱动的兼容维护成本抬高整整一个数量级。如果需求仅仅停留在炮口闪光、护盾受击波纹或常规光影增强，**优先利用原版粒子、自定义贴图或社区现成的静态光照贴图接口就能以极低成本解决**，大可不必上来就重写整套底层渲染。

## 直面裸 GL 状态机，与借用高层渲染方案的取舍

真正绕开游戏原有的常规绘制封装去操纵显存与着色器管线，等于把原版平时替您默默遮住的脏活全部接回自己手里：OpenGL 状态切换保存得不干净就会当场污染全屏贴图与战场界面，着色器里声明却未参与最终像素输出的变量会被显卡驱动编译器顺手优化裁掉，缓冲绑定与索引槽位的连带改写稍有不慎就会互相冲撞，甚至已经标记移除销毁的底层渲染实体绝不能再被重复塞回渲染队列。

把底层数据流、显存对象与着色器绑定逻辑从头走通，核心目的在于彻底看明白这笔显存、算力与状态的底层账目；而在真正写工程代码时，**先将通用状态保存恢复与显存判空清理抽进极薄的公共基类，不要把脆弱的裸状态操作散进业务代码各处**。一旦理解了管线里每一处开关在管什么，日常开发更不必永远死磕全套手写裸 OpenGL：**凡是成熟社区高层渲染库能够稳妥接管的实体生命周期、绘制队列调度、模型与多源光照，直接交给高层方案才是更清醒的工程选择。** 至此，全书将工具下限到图形深水区的完整掌控权交到您手上，往后每一分视觉表现背后要付出的工程代价，也就全都在您自己的计算之中了。
