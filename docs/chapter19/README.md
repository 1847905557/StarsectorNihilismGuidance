# 可选兼容与设置集成

本章技术基线：Starsector `0.98.5a-RC3` 与 Java 17；可选依赖基线：LunaLib `2.0.5`、Nexerelin `0.12.1e`。

---

随着生态逐步成型，一部分大型社区前置与玩家向设置面板几乎成了常规玩家清单里的常驻成员，却又不能假定所有使用场景都必然安装它们。当这些框架在场时，它们远不止提供几行辅助工具函数，实际上会直接接管星区开局、战略扩张、外交格局乃至实时热更新参数控制流，构成一整套并行体系。

## 双轨运行下的隔离适配与参数克制

处理可选接入，工程上真正要解决的是类加载边界与控制流双轨并存问题。只要外部扩展接口的符号直接泄露进主工程入口类的公开签名、字段或早返回分支里，在缺少对应依赖库的环境中启动游戏时，虚拟机就会在进入启用判断之前提前触发类加载失败。

**正确的兼容边界是编译期引入外部接口作为参照，打包时不把第三方类打进自身产物，运行期先核对启用状态再踏入嵌套隔离适配器。** 同时对于设置面板集成，也不要把工程里所有内部常数一股脑都抛给配置面板让玩家决定：**只筛选少数真正适合实时微调手感、显示表现或功能开关的参数放进面板，其余保持由同一套默认常量路径在无该前置库时接管**，才能既保证热调优体验又不破坏核心设计的一致性。

## 识别第三方前置里的静默回退与实机验证

把隔离边界搭好只是第一步，真正容易让开发者误判的地方，在于大型三方框架普遍带有一套与原版直觉完全不同的隐藏行为：未成功注册的势力或产业配置查询往往不会返回空值，而是静默回退成中立或默认条目，把键名拼错彻底掩盖过去；开新档流程里弹出的实时设置面板，底层甚至故意绕开了热更新变更回调；某些战略规模接口内部也已经预先叠过全局倍率。**接入这类大型框架时，绝不能仅凭配置字面无误或代码编译通过就默认联动已经生效：务必核对底层实现与返回对象的真实标识，并在游戏内配合日志与真实开局把行为逐项测实。**
