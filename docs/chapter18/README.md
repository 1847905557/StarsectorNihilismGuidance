# 常用依赖库

本章技术基线：Starsector `0.98.5a-RC3` 与 Java 17；依赖基线：LazyLib `3.0.0`、GraphicsLib `1.12.1`、MagicLib `1.5.6`。

---

跨过原版机制的基本盘之后，大多数 MOD 迟早都会面对同一批重复劳动：二维向量与战场目标检索、脱离单份存档的通用 JSON 持久化、光照贴图映射、弹体多段尾迹乃至数据驱动的悬赏委托。社区主流前置库正是把这些高频基础设施打包成了公开入口。

## 省掉了重复实现，绝不免除半分责任

接入外部库之前，先把最关键的一条账算清楚：**社区依赖库替您省下的只是重复造轮子的体力活，参数口径、对象归属、状态边界与资源清理的责任，一丝一毫都不会替您免除。**

在实际调用中，外部库并不会因为挂着常用工具的名号就自动替用户避开错误用法：名字相近的几何方法可能直接原地改写传入的向量对象，也可能直接把实体内部持有的私有引用裸露返回；写入公共配置目录下的文件在格式损坏时可能悄然被默认模板整份覆盖。**针对这类隐患，稳妥的习惯是在不确定入参或返回值归属时先做一次复制，在宿主销毁回调里主动补上动态光源或尾迹的收尾动作，并在外置数据异常时保留备份与安全检查**，而不是指望第三方接口自动替您擦干净痕迹。

## 正视原版依赖机制与社区前置里的反直觉设计

同样不必因为工具普及就去美化整套链路的实现质量。一方面，**原版启动器在解析与展示外部依赖时就带着相当反直觉的设计**：依赖声明里的版本号并不等同于最低兼容下限，实际运行是按主、次、修订号逐段比对，主版本不同直接阻断启用，哪怕只是修订号高出一点也会在勾选列表界面亮起刺眼的黄色警告。**考虑到前置依赖的更新节奏，实战中更稳妥的做法是在声明里干脆省略具体版本号，仅凭稳定库标识确认前置存在即可**。

另一方面，社区前置库自身经过多代版本迭代，也同样残留着各自的历史习惯与隐蔽限制：同类弹体多条配置往往直接沿用首条记录的采样参数、底层贴图修改不会主动刷新外部材质缓存、局部工具在读取到残缺配置时也可能默默用默认模板覆写。外部能力既可以通过静态数据表交由加载器集中接管，也可以在运行期由代码按需创建提交。动手接入前先把两者分工界线、加载前置条件与错误回退口径交代明白，才不会在依赖版本更迭或排查日志警告时抓瞎。
