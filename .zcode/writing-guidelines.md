# Writing Guidelines

本文件规定 `docs/` 教程的作者表达、读者基础、页面组织与教学职责。文字呈现见 `.zcode/text-guidelines.md`，技术事实与成品要求见 `.zcode/technical-guidelines.md`，固定用词见 `.zcode/terminology.md`。

## 作者表达

- 以当前仓库中本次涉及的文章和同类文章为依据，完整阅读相关上下文，按需要参考在线文章。
- 从操作引导、技术解释、创作立场、节奏、反问、幽默和强调各自承担的职责判断风格。
- 技术说明必须写清对象、动作、条件、关系与结果，操作引导交代位置、当前动作和成果的观察时机。
- 命名、美术、配置、数值、手感、工具和教学取舍可以表达明确立场，评价给出具体对象、依据和代价。
- "编者建议" 用于影响实现选择的关键建议、立场，或有上下文依据的暗指。
- 口语、尖锐评价、自嘲、反问、夸张和冷幽默依附实际操作、事实或创作判断，保持信息与操作连续。
- 预判、暗指和措辞回环有铺垫和落点，反问在当前语境中给出回答、观察方法或立场。
- 命令、日志原文、参数和可执行代码保持准确，故障分析直接说明症状、原因、检查位置和修正动作。
- 对读者使用 `您`；`编者` 表达经验、审美、判断和亲自观察；`我们` 表达共同操作；`用户` 指 MOD 的最终使用者。
- 技术限制说明条件与后果，创作建议说明理由和取舍，表达力度取决于具体语义。
- 机制解释使用当前对象的实际关系，作者评价中的形象措辞按上下文理解。

## 读者与教学节奏

- 第 1–5 章面向具有游戏经验、正在学习制作流程的读者，首次文件、注册与代码操作交代位置和修改方式。
- 第 6 章及以后以基本 Java 语法和构建知识为前提，重点讲清游戏对象、调用时机、数据流和生效条件。
- 再次使用同类操作时指明沿用内容，集中解释新增差异、原因、风险和结果。
- 先给当前动作，再解释完成动作所需的信息；机制讲解交代谁提供、谁读取、何时生效和怎样观察。
- 示例数值与资源选择说明设计理由和代价，讲解深度符合当前任务与读者基础。
- 段落围绕操作、因果或条件关系展开，句序与长短顺着读者当前的疑问组织。
- 首次完整讲解负责概念定义，后续使用指向真实前置知识，前置成果对应读者已经完成的工作。
- 根据教学任务选择正文、列表、表格、局部片段或完整成品，数量取决于内容需要。

## 页面结构

### 首页与章页

- 首页说明教程用途、读者与阅读入口，内容服务教程整体。
- 章页必须采用 H1 → 本章技术基线 → 章介绍 → H2 `本章各节` → 自动列表占位符。
- 章介绍用 3–4 个自然段展开共同主题、实际用途、能力边界与理解重点，依据所属各节的教学职责组织。

### 节页

- 节页必须采用 H1 → 引言 → 阅读时间 → 操作时间 → 学习目标 → 前置知识 → 正文 → 适用的验证方案 → 故障分析 → 总结 → 建议参考项。
- 固定页面章节使用 H2 `学习目标`、`前置知识`、`验证方案`、`故障分析`、`总结` 和 `建议参考项`，多成果验证在对应成果后使用 H3。
- 引言用一个自然段交代对象、值得处理的问题和本节工作，前文承接服务当前任务。
- 阅读与操作时间各占独立斜体段落，位于学习目标之前，源码采用 `\~数字 分钟`；纯概念页按实际投入填写操作时间。
- 学习目标必须用可验证动作描述能力或成果，每项承担一个主要能力。
- 前置知识在标题后直接使用平级列表；教程内知识以 `[C数字-S数字]` 开头并说明内容，外部知识直接说明。
- 软件安装、存档和测试对象等环境条件归入适用验证的前置数据，前置知识对应读者已经掌握的内容。
- 总结用自然段提炼本页已有的任务、关键判断、对象关系或可复用方法。
- `建议参考项` 是最后一个 H2，每项采用项目符号、行内代码对象和冒号说明，交代参考对象与当前任务的关系。
- API 参考项使用完整包名与类名，方法放在所属类的说明中，冒号前为实际参考对象。
- `starsector-core` 内的文件和次级目录使用相对该目录的路径；其根目录直接文件、一级目录本身及外部位置使用从 `Starsector/` 开始的路径。

## 正文与引用

- 正文按读者完成任务的顺序展开，标题表达动作、判断、关系、现象或宽泛主题。
- `文件与 API 链路` 和 `完整最小例` 在确有相应内容时使用 H2。
- `完整最小例` 包含简短引言与完整产物，机制解释和所需局部代码在操作正文中就地展开。
- 正文中的章节引用用于直接操作依赖、共享 ID、对象来源、机制衔接或故障原因定义，并交代当前关系。
- 验证中的章节引用用于获取前置对象与资源，动作目标、路径、数值、触发条件和预期结果写在当前方案中。
- 速查表与规则自含判断需要的信息，导航对应实际技术关系。
- 定义与字段映射使用自然语言，等号用于计算、换算和数值核对。

## 验证方案

- 可运行或可观察成果必须提供验证动作与预期结果，单一成果集中确认，多成果分别确认；概念页按实际可验证成果组织。
- `前置数据：` 补充上下文尚未明确的 MOD、存档、配置或对象，条件已明确时直接进入动作。
- 验证动作使用紧凑有序列表，每项承担一个连续阶段，写明入口、时机、目标与观察位置。
- 构建、启动、重启、新档、界面和战斗操作按生效条件安排，步骤数量对应独立成果与操作需要。
- 动作后使用 `预期结果：` 与紧凑项目列表，给出可观察的对象、数值、日志、画面或行为。
- 预期结果逐项对应成果，相同成功条件合并，故障演示要求出现的原始错误单独列出。
- 验证截图放在预期结果之后，附观察说明。
- 涉及加载失败、数据损坏或不可逆结果时，步骤必须写明恢复动作与目标值；还原本身为验证目标时作为独立操作。
- 验证通过稳定示例入口观察，恢复指引对应实际风险或所验证的撤销行为。
- 教程验证呈现读者能够执行的操作与预期结果。

## 故障分析

- 故障分析位于总结之前，标题后直接进入可区分的症状列表。
- 故障条目必须采用 `- **症状**：原因` 主行，写明触发条件和原因；紧随子行采用缩进 4 空格的 `- **解决方案**：核对与修正`。
- 每项在修正动作处结束，条目之间保留空行。
- 故障引用使用症状主题，解决方案给出实际检查位置与修正动作。
