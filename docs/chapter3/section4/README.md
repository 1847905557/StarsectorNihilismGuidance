# 补完描述文本

**可读性大于一切**。

这不含任何夸张成分，所以任何一个该给玩家使用的 MOD 里都不应该出现任何一项 `No description... yet`。该让我们刚建好的巴别塔倒塌了。

---

_本节预期阅读时间：\~15 分钟。_

_本节预期操作时间：\~20 分钟。_

## 前置知识

- [C1-S7] 的 `descriptions.csv`，八列表头、类型与转义规则，本节在同一份文件里继续追加；
- [C3-S1] 的势力 `gear_industry`，本节为它补上描述；
- [C2-S3] 的突击填弹器与抵抗力场，本节补全它们的系统说明列；
- [C3-S3] 的 `GearInSystemGenerator.java`，行星描述要在其中绑定。

## 为势力写描述

绝大多数前文未介绍过的文本，都和舰船、武器的描述一样写在 `data/strings/descriptions.csv` 中。打开 [C1-S7] 创建的这个文件，**追加前确认首行的八列齐全，没有缺失或多余**，否则下面各列的说明会与您的文件对不上。

[C3-S1] 的情报界面里，齿轮工业的描述一栏还是 `No description... yet`。在文件末尾追加：

```csv
gear_industry,FACTION,"齿轮工业是一个大崩塌后聚集而成的工业集团，主要由家底深厚的拾荒者与落魄财团领导人牵头。他们热衷于通过各种渠道搜集古早蓝图并根据现状加以修改，但据称这只不过是为了避免专利诉讼。",,,,,
```

**势力描述的 `id` 就是势力文件的 `id`，`type` 为 `FACTION`。** 情报界面只读 `text1`，其余列留空。

::: tip 稳定性建议

**总是**为所有文本都用一个最大层级的双引号进行包络，这样就能避免一切双引号错误。

不使用英文逗号和句号也可以避免错误，并且让文本显得美观。

:::

编者在这段话里写了齿轮工业的来历和一个传闻，没有写它的舰船有多强。**势力描述写来历与性格，战力留给舰队去证明。** 玩家在星图上遇见齿轮工业两三次之后，自然知道它打起来是什么样子；描述里写 "装备精良、战斗力强大"，只会在玩家第一次打赢它时变成笑话。

### 进游戏核对

保存文件，重启游戏，读取任意存档。在情报的势力页选择齿轮工业，右侧的描述应当换成上面的正文。

## 为战术系统补全各列

[C2-S3] 的突击填弹器与抵抗力场已经装在工匠上，但装配界面里的系统说明仍是占位文字。战术系统的描述用到的列比舰船多：

| 列名    | 用途                                                         |
| ------- | ------------------------------------------------------------ |
| `text1` | 数据库中的详细说明                                           |
| `text2` | 系统类型，数据库按它分类。原版使用 `进攻`、`防御`、`机动` 等 |
| `text3` | 装配界面的简略说明，留空时显示 `text1`                       |
| `text4` | `text3` 中需要高亮的文字，多段用 `\|` 分隔                   |
| `text5` | 数据库中的效果说明，`{{...}}` 包住的部分高亮显示             |

突击填弹器的原型是原版的加速填弹器，它的一行可以对照着看。`进攻` 在 `text2`，短说明在 `text3`，带 `{{...}}` 的效果说明在 `text5`：

```csv
ammofeed,SHIP_SYSTEM,激活一种先进但不持久的装置，用以快速装填实弹武器。该装置再次使用前必须重新校对并等待冷却完毕。,进攻,降低实弹武器所产生的幅能，并提高实弹武器的射速。,,提升 {{100%}} 的实弹武器射速，并降低实弹武器 {{50%}} 的幅能产生。,
```

在文件末尾追加两个系统的描述：

```csv
GearIn_assaultfeed,SHIP_SYSTEM,"在短时间内向供弹机构与推进器超量输送功率。实弹武器的射速大幅提高、开火幅能降低，舰船也能更快地接近和转向。",进攻,"提高实弹武器射速与舰船机动性，并降低实弹武器的幅能产生。",射速|机动性,"提升 {{100%}} 的实弹武器射速，并降低实弹武器 {{50%}} 的幅能产生。
最高航速提高 {{50}}，加速与转向能力提高 {{200%}}。",
GearIn_resistfield,SHIP_SYSTEM,"工匠的实验性抵抗力场。启动后在船体外层形成一层力场，削弱来袭的伤害，对高爆与 EMP 伤害尤其有效。",防御,"降低舰船受到的伤害，对高爆与 EMP 伤害效果更好。",高爆|EMP,"高爆与 EMP 伤害减免 {{75%}}，动能与能量伤害减免 {{50%}}。",
```

`text4` 写的是 `text3` 里的原文片段，**高亮按文字匹配，片段必须与短说明逐字一致。** 写成短说明里没有的词，游戏不报错，只是什么也不亮。

**`text5` 里的数字是手写的，不会跟着效果脚本变。** 以后在 [C2-S3] 的脚本里把 `ROF_BONUS` 改成别的值，数据库照样显示 `100%`，游戏不会提醒您。船插的描述能用 `%s` 从代码取数，战术系统的效果说明不能，改数值时要记得回来改这一行。编者的习惯是改完常量立刻搜一遍系统 ID，把描述一起改掉。

短说明是玩家在装配界面最常读到的那一句，编者把它写成 "做什么、对什么最有效"，细节和数字都放进 `text5`。

### 进游戏核对

保存文件并重启。用控制台 `Addship GearIn_artizan` 取得一艘工匠，打开装配界面：

- 系统一栏显示短说明，"射速"、"机动性" 高亮；
- 在数据库中打开突击填弹器与抵抗力场，分别归在进攻与防御类，效果说明中的数字高亮。

## 为行星写描述

[C3-S3] 生成的两颗行星，现在悬停时显示的是原版类地行星和贫瘠行星的通用描述。**行星的 CUSTOM 描述属于具体行星，PLANET 描述属于行星类型。** 原版 `terran,PLANET` 一行写的是所有类地行星的共性，Nipher Prime 要有自己的故事，就得给它一条 CUSTOM 描述，再在生成器里把两者连起来。

在描述文件末尾追加：

```csv
GearIn_planet1,CUSTOM,"这里曾经是无数个零散组织的根据地。直到后来被统一，此地稀有矿藏的开采权一直被转让于几个大型武装团体之间。",,"轨道交通管制井然有序，通讯频道里一刻不停地播报着货运排期与工坊的招工启事。",,,
GearIn_planet2,CUSTOM,"一颗荒芜的行星，因战略价值极低而在近百年内遭到各大势力的忽视。地底埋藏着零散的矿业资源。",,"地表扫描只返回零星的矿脉信号。除此之外，这里什么也没有。",,,
```

`text1` 是悬停与详情面板中的正文，`text3` 是舰队接触行星时，交互面板里显示的文字。

CUSTOM 描述的 `id` 是描述本身的 ID，不一定要和任何实体相同；原版 Asharu 的描述键就是 `planet_asharu`。编者让它与行星 ID 相同，查起来省事。

然后打开 [C3-S3] 的 `GearInSystemGenerator.java`，在创建两颗行星的语句之后加入绑定：

```java
prime.setCustomDescriptionId("GearIn_planet1");
second.setCustomDescriptionId("GearIn_planet2");
```

**改描述文字只需重启，改绑定要开新档。** 文字在游戏启动时读取，已有存档读进来就是新文字；绑定写在生成器里，只在创建新生涯时执行一次。以后凡是 "在代码里把某个对象连到某条数据" 的写法，都要先想清楚它在什么时候执行。

原版大部分无人居住的行星都没有自己的描述，用的就是类型描述。编者给 Nipher Second 也写了一条，因为它是齿轮工业星系的一部分，玩家第一次进星系时会逐个悬停；代价是每多一条，以后改设定时就要多改一条。

### 进游戏核对

保存描述文件与生成器，重启游戏，创建一个新生涯，进入 Nipher：

- 悬停 Nipher Prime 与 Nipher Second，正文换成各自的 CUSTOM 描述；
- 驾船接触两颗行星，交互面板中出现 `text3` 的文字。

## 描述类型速查表

**`id` 和 `type` 共同确定描述。** 同一个 ID 可以同时拥有 `SHIP` 与 `SHIP_SYSTEM` 两条描述，互不干扰。

**同一列在不同类型中承担不同职责。** `text2` 在战术系统里是分类，在武器里是署名，在势力里根本不读。填写之前，先确认对象属于哪一种类型。

| 类型             | `id` 来源                                    | 主要显示位置                   |
| ---------------- | -------------------------------------------- | ------------------------------ |
| `SHIP`           | 船体 ID，或船体的 `descriptionId`             | 舰船与战机详情、装配、蓝图     |
| `WEAPON`         | 武器 ID                                      | 武器详情、装配、数据库         |
| `SHIP_SYSTEM`    | 系统 ID                                      | 装配系统一栏、数据库系统详情   |
| `FACTION`        | 势力 ID                                      | 情报的势力页                   |
| `PLANET`         | 行星类型 ID，或类型的 `descriptionId`        | 行星与恒星悬停、详情           |
| `CUSTOM`         | 自定的描述键，由 `setCustomDescriptionId` 绑定 | 具体实体的悬停、详情与交互面板 |
| `RESOURCE`       | 商品 ID                                      | 货舱与交易界面                 |
| `ASTEROID`       | 固定为 `asteroid`                            | 小行星悬停                     |
| `TERRAIN`        | 地形 ID                                      | 星云、小行星带等地形悬停       |
| `ACTION_TOOLTIP` | 战斗指挥命令的小写名称，例如 `assault`       | 战斗指挥命令悬停               |
| `GALLERY`        | `illustrations` 分类中的贴图键               | 数据库图库                     |

不在表中的对象，描述不写在这个文件里，而是写在它们各自的 CSV 中：

| 对象     | 描述所在位置                                    |
| -------- | ----------------------------------------------- |
| 船插     | `data/hullmods/hull_mods.csv` 的 `desc` 列      |
| 市场条件 | `data/campaign/market_conditions.csv` 的 `desc` 列 |
| 特殊物品 | `data/campaign/special_items.csv` 的 `desc` 列  |

::: tip 皮肤与描述键

`.ship` 与 `.skin` 都可以用 `descriptionId` 指向另一条 `SHIP` 描述。**字段改变的是描述查找键，船体注册仍使用原来的船体 ID。** 编者在基础船体上保留默认描述键，在皮肤需要独立说明时才使用这个字段。

:::

## 常见问题

- **情报界面中齿轮工业的描述仍是 `No description... yet`**：描述行的 `id` 与势力文件的 `id` 不一致，或 `type` 没有写成 `FACTION`。
    - **解决方案**：对照 `gear_industry.faction` 的 `id` 修改，保存后重启。

- **装配界面的系统短说明没有高亮**：`text4` 中的片段在 `text3` 里找不到，或多段之间没有用 `|` 分隔。
    - **解决方案**：从 `text3` 中复制要高亮的原文到 `text4`，保存后重启。

- **战术系统在数据库中归错了类**：`text2` 为空或写了原版没有的分类名。
    - **解决方案**：参照原版战术系统的 `text2` 填写分类，保存后重启。

- **改了效果脚本的数值，数据库里的数字没变**：`text5` 是手写文本，不读取脚本。
    - **解决方案**：同步修改描述行中的数字。

- **行星仍显示类型描述**：使用的是加入绑定之前的存档，或 `setCustomDescriptionId` 的参数与 CUSTOM 行的 `id` 不一致。
    - **解决方案**：核对两处键名，创建新生涯后再看。
