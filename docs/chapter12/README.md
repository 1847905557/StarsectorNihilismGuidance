# 市场与商品

本章技术基线：Starsector `0.98.5a-RC7` 与 Java 17。

---

对玩家而言，一座殖民地无非是一处能停靠、买卖货物、顺手接两单补给的空间站或星球；但在星区底层，所谓经济模拟并不靠无数货船逐箱搬运实物来维系，而是把实体、账户、交易界面、产线与环境修正拆进彼此独立的多层结构里，再凭手工注册与互相引用拼成一套运转链路。

## 为什么会做出一个 "不会报错的空壳"

这套经济体系最容易在调试阶段失手的地方，是各层之间大量采用单向绑定与延迟接线，而游戏在加载或生成星系时几乎不做完整性自检。**空间站实体放进星图、市场登记进全局经济系统、具体交易入口与产业挂上市场，这几环里但凡漏掉一处反向引用，游戏既不会抛异常，日志里也干干净净**，玩家飞到站点门口面对的却是一个无法正常交易的空壳。排查这类断链时，最省心的顺序就是顺着 "实体指向市场 → 市场加入经济系统 → 子市场与产业挂回市场" 这条主线逐环核对。

商品和产线的运作同样建立在抽象档位之上。除非打算全面大改整片星区的经济系统，**新增商品时最稳妥的做法是直接归入原版相近的需求大类与经济档位换算基准里，借用现成供需模拟器运转**，而不必硬造一套孤立价格算法。此外，产业在缺乏原料、处于建造队列或遭破坏停工时，底层基类并不会自动将产出清单清零，必须在有效条件之外亲手清空产出，否则站台停工期间仍会在后台继续输出物资。

## 跨越存档周期与实例隔离的稳妥存储位置

当自定义特殊物品与市场条件介入这套链路后，最棘手的边界转移到了对象生命周期上。**真正改写产出的特殊物品效果对象，在游戏启动时便作为全局单例常驻于进程之中，绝不会随读档和切换存档而销毁重建。**

一旦在效果类自身字段里缓存某个具体市场或生涯状态，就会立刻引发跨存档污染；**如果这类效果或产业真的需要随特定市场记录动态状态，正确的存放位置是每次回调传入的市场自身键值容器里，而不是留在全局效果类的成员变量中**。同样地，作用在市场上的动态条件也必须依靠实例化的来源标识写入数值修饰，确保同类型多实例并存时各自记账、不会悄悄互相覆盖。
