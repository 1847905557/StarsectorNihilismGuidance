# Writing Guidelines

本文件规定 `docs/` 教程的读者预设、作者语气、段落推进与页面组织。文字格式与固定条目语法见 `.zcode/text-guidelines.md`，技术事实与示例契约见 `.zcode/technical-guidelines.md`，领域用词见 `.zcode/terminology.md`。

## 两阶段标尺与读者预设

- 全书以 `C6` (Java 工程化) 为分界，分为两档语气与讲解深度。两档整体接近资深开发者撰写的 Geek 技术博客，共享首页 `docs/README.md` 的作者底色：门槛很低，标准很高；判断力比热情重要；重视尺度和分寸。
- **第 1–5 章 (锚定 `C1`)**：预设读者有游戏经验、无编程与制作基础。首次出现的文件路径、目录层级、工具操作与注册步骤写清位置与改法，代码片段可附解释每行作用的行注释。允许如实写出外行面对陌生代码或复杂界面时的真实冲击 (例如 "内容简直令人眼花缭乱")，但不作脱离事实的夸张。
- **第 6 章**：承担工程化分水岭，交代从游戏自带编译到独立 Java 工程的切换，并明确此后不再解释基础 Java 语法。
- **第 7 章至末尾 (锚定 `C7`)**：预设读者具备扎实的编程与工程经验，主体围绕代码与运行机制展开。保持 Geek 技术博客式的叙述流畅度，行文干脆、自然、不僵硬，直接交代游戏对象、调用时机、数据流、状态边界与代价；同类操作指明沿用哪一节，只讲新增差异，不替基础概念做铺垫。

## 作者立场、语气与风味

- **立场先于说明**：编者是带人做成一件事的老手，不是写字段说明的客服。每页动笔前，先从正文抽出本节真实做过的取舍 (想要什么、看不上什么、哪里会静默翻车)；写不出具体取舍，说明这一页还停在字段说明书，必须回到正文重写。
- **自然陈述，不贴标签**：取舍、理由与代价随叙述自然带出，不写 "编者的取舍"、"编者的态度"、"编者的要求" 这类自指说法，也不把风格名词拿来给句子贴标签。核心取舍写透，顺手的参数或资源沿用一笔带过，不在细枝末节上刻意拔高；"编者" 分量极重，只在表达强烈个人判断时使用 (如 "编者认为"、"编者倾向于")。
- **身份与距离感**：对读者用 `您`，作者经验与审美用 `编者`，共同操作用 `我们`，MOD 使用者称 `用户`；严禁使用 `你`。不迎合、不安抚、不祝贺，也不将读者置于与编者对等的位置；常见错误直接点明即可，不靠否定别的东西抬高当前内容 (如 "不是 X，而是 Y"、"再好也比不上")。
- **书面语为底，留出叙述润滑与点睛空间**：正文以顺畅的书面语为底，保留适当的叙述性润滑，像人在认真写一篇技术长文，既不滑成群聊口水话，也不写成干瘪僵硬的说明书。闲聊或调剂性过渡 (例如带收回意图的 "扯远了") 原则上留在章导语与节导语，用来立调子、防枯燥；正文内部只可在关键提醒或节奏节点处克制地留少量提醒或 `point punch`，点到即止以打破单调，禁止连篇碎嘴、空洞热场或脱离事实的夸张比喻。顺句时区分无意水词与有意玩梗，导语或过渡里保留的梗本身不得丢失；遇到作者有意识提出或强调的设计概念词，保留原词并就地给出简明定义，不替换为平庸词汇；存量文本中偶见的递进叠词或就表达、篇幅限制的坦白说明，遇到时保留即可，不作为常规手法刻意模仿。
- **严禁拟人，彻底严禁**：程序对象不得拥有感知 (看得见、读得到)、意愿 (想、要、决定)、记忆 (记得、认得)、生命 (活着、寿命、活多久) 或社会行为 (允许、拒绝、等待、被叫住、团结)。检查方法：找出动词主语，只要主语是程序对象而动作只有人才做，就把动作还给引擎、游戏或调用方。
- **克制数字、修辞与虚夸**：不预先报数 (如 "需要确认两件事"、"有三个原因")；数字只在参与文章结构或读者实际要用时出现，随游戏更新变化的枚举总数不写，按用途分类。不凭空拔高立意 (拔高仅限最关键的工程节点，且不超过现有程度)；不用破折号替代逗号作插入语。
- **限制与建议分离，缺口当场交代**：硬性限制写清触发条件与后果，创作建议写清理由与代价，让读者分清哪条必须遵守、哪条可以不听。技术底线必须硬截止；非底线的创作思考允许偏软的留白表达，给读者留出思考空间，不强求句句硬收。存在矛盾、没有截图或没有速查表等缺口时直接说明，不加包装。

## 依赖库章节

- 原版章节首次用到依赖库时，只简短说明用途、启用方式与当前用法，详细拆解留给对应依赖库章节，并以 `[C数字-S数字]` 指向它。
- 依赖库章节围绕 "这个库替您省掉了什么" 与 "省掉之后哪些判断仍由 MOD 自己承担" 组织，片段服务实际需求，不逐个罗列 API 方法。

## 页面组织

### 章页

- 固定结构为唯一 H1、紧接 H1 的 `本章技术基线` 段落、章介绍与 `## 本章各节` 下的自动列表占位符。**章页标题与节页 H1 一律沿用现行标题，不重写、不改动。**
- 章介绍站在整章高度讲清这一层在 MOD 制作中的位置、核心矛盾与编者态度；不写具体文件、字段、类或命令，不预告各节顺序，不复述节成果清单，也不以按需选读的导览句收尾。

### 节页

- 固定顺序：唯一 H1 → 导语 → 空行 → 分割线 `---` → 阅读时间与操作时间两个斜体段落 → 正文 H2/H3 (第 6 章起首个 H2 必须为 `## 前置知识`) → 可选 `## 常见问题` → 结尾 `## 建议参考项` (第 6 章起推荐；第 1–5 章凡复制或修改过原版文件同样应给出)。
- 导语站在动手之前，基于本节取舍起调，不预告步骤，不复述后文细节、数值或完成后的状态；可以点出关键接口名，但单句内超过两个行内代码标记就说明在罗列而不是在说话。
- 同章内各节的开头切入、段数与收法随题材变化，禁止把某一页的写法归纳成固定模板再套给同章其他节；短促强烈的收法全教程至多出现一次，用过不再复用。
- 正文按制作与验证顺序组织，H2/H3 写动作或对象；主要成果的设计取舍 (意图、数值或行为代价、实测评价) 随叙述自然带出，不单设 "设计取舍" 小标题；次要成果一句带过或不写。
- 每个可运行成果都在出现位置写清游戏内确认，说明进入方式、操作与应看到的现象；确认所需的路径、数值与触发条件就地写全，不让读者翻回前文找。
- 禁止使用 `## 学习目标`、`## 总结` 或复述本页内容的收尾段落。

### 前置知识

- 标题后直接写列表，只列读者真正需要先完成或掌握的内容；测试存档、已装 MOD 等环境前提写在游戏内确认处。
- **条目里只要出现 `[C数字-S数字]` 引用，它必须是该条目的第一个元素**，其后说明用到了什么，且**只引用本节之前的内容**；后续章节或同章后续小节才讲的知识不列入此处，需要时在正文就地讲清。
- 全书通用规则只在读者首次实际用到的页面列出，后续页面不再重复；第 1–5 章存在前置依赖时同样列出。

### 常见问题

- 只收录本节操作真实会触发的报错与症状，原始报错文本保持原样；格式见 `.zcode/text-guidelines.md`。

### 建议参考项

- 按单节独立核计，列出与当前任务直接相关的原版文件或 API 类；凡本节实际复制、参照或修改的原版文件，不因前节已列而省略，每项均须核对其真实存在。具体格式与路径约定见 `.zcode/text-guidelines.md`。

## 引用与防漂移刹车

- 章节引用 `[C数字-S数字]` 用于前置操作、共享 ID、对象来源或机制衔接，并交代当前关系；机制讲解交代谁提供数据、谁读取、何时生效、在哪里看到效果，示例数值与资源说明设计理由。
- 重写或校审一章前，逐节核对：是否写清本节真实取舍、语气是否落在所属阶段标尺 (`C1` 或 `C7`)、叙述是否保持流畅而未滑向机械说明书或碎嘴口语、闲聊过渡是否留在导语而正文 `point punch` 克制、同章相邻节的开头与收法是否撞模板，以及是否未盲信或转述原版 javadoc 或源码注释 (仅当原版注释本身出错且会误导实操时点明纠偏)。
