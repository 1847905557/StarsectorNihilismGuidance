# Writing Guidelines

本文件规定 `docs/` 教程的语气、读者基础与页面组织。文字呈现见 `.zcode/text-guidelines.md`，技术事实与成品要求见 `.zcode/technical-guidelines.md`，固定用词见 `.zcode/terminology.md`。

## 语气

- 语气与首页 `docs/README.md` 一致：直接、口语、有作者立场。
- 立场先于说明：编者是带人做一件事的老手，不是给对象写说明的客服。每页动笔前，先从正文里摘出编者做过的取舍：想要什么，看不上什么，为什么这样设计。这些取舍决定导语、加粗句与评价，写不出取舍的页面，说明它还只是字段说明书，需要回到正文重写。
- 编者的底色来自首页：门槛很低，标准很高；判断力比热情重要；对评价不在乎，只是想做。每页的语气都是这套态度落在具体题材上，不单独成句宣讲，也不换成安抚或鼓励。
- 做法是先复制、先动手、边读边猜、进游戏核对，难处与缺口当场说出来：矛盾、没做到的事、没有截图、为什么这一节没有速查表，都直接交代，不包装。
- 页与页的开头、段数、收法各不相同，随题材而定。禁止把某一页的写法归纳成句型再套给别页。短促强烈的收法全教程至多出现一次，已用过的不再使用。
- 不拔高立意：不用 "玩家记住一个势力，常常是因为..."、"不少 MOD 正是输在这里" 这类凭空的大判断去连接题材，开头直接从本节的对象与做法说起。拔高立意只可能出现在最关键的章节，如 Java 工程化，且以那一章现有的程度为上限。
- 不用风格特征的名称当写作依据，也不用它们给自己的句子贴标签。
- 立场与选择自然地说明并使用，不每次强调。不写 "编者的取舍"、"编者的要求"、"编者对 X 的态度" 这类给做法贴标签的说法。"编者" 用于强调立场时分量极重，只在立场极其强烈时使用，如 "编者认为应该"、"编者倾向于"；多数取舍直接陈述。写完一页，只问两件事：编者的立场是否出自本节的具体取舍，读起来是不是同一个人在说话。
- 先说现在要做什么，再说为什么。例如："制作舰船首先需要一张贴图。"
- 遇到真实困境时点明，再给出解决办法。例如："若需要制作舰船的装配，则最好的方法却又往往是从战役里导出。这种先有鸡还是先有蛋的问题可以被**测试战役**解决。"
- 能借用原版时，先复制一份原版文件，再逐项改成自己的。例如："首先随机挑选一个原版战役，将它文件夹里的所有东西都复制到 `GearIn_test` 文件夹内，然后逐个文件进行修改。"
- 主要使用书面语。口语可以用，但必须保持每个字的重要性，且绝不落入俗语或闲聊腔。例如：
    - "那之后，大概就是**地狱**。"
    - "普通玩家眼中的 '大佬' 其实非常好当。"
    - "如果您并不了解上述内容，请去学习它。"
- **严禁拟人，彻底严禁。** 程序对象不得被赋予感知 (看得见、读得到)、意愿 (想、要、决定)、记忆 (记得、认得)、生命 (活着、寿命、活多久)、社会行为 (被叫住、自己会、允许、拒绝、等待)。判断方法：找出每个动词的主语，问它是不是程序对象，再问这个动作是不是只有人才做。写法上把动作还给引擎或游戏，对象放在宾语位置。
- 直接写出内容，不预先报数，如 "需要确认两件事"、"有三个原因"。
- **数字只在参与文章结构或读者会用到时才出现。** "十九个常量的枚举" 这类计数不写：读者既不用记，也不影响怎么用，游戏更新一次就要跟着改。按用途分类，不报总数。
- 编者可以有立场，但评价落在具体对象上，并说明理由或代价。例如："**编者并不擅长画图，但刚好也能展示获取贴图对于绝大多数人来说都不是一件困难的事情**。"
- 编者与读者的身份和高度保持着不可逾越的距离感：
    - 对读者用 `您` 保持距离，作者的经验、审美和判断用 `编者`，编者带领读者操作用 `我们`，MOD 的最终使用者称 `用户`。
    - 不讨好读者；可以预设读者的感受，但不体贴、不安抚；不祝贺读者或将其置于与编者同等的位置。
    - 距离感来自见得多：编者什么都见过，以后还会反复见到，因此与读者少有可轻易共情之处，对常见错误见怪不怪。
    - 编者用自然的语言以绝对正确的姿态进行叙述，无需强调、论证、长篇解释。
- 立论用肯定句，不靠否定别的东西来抬高当前内容，如 "不是 X，而是 Y"、"再好也比不上"。
- 技术限制和创作建议分开写：限制说明条件与后果，建议说明理由与取舍，读者能分清哪条必须遵守、哪条可以不听。
- 句子写清对象、动作和结果。少写空泛的总起与收束，一段讲完一件事就进入下一件。
- 破折号是强强调，不是插入语标记。把破折号当逗号用，等于每段都喊一次，语感会被打碎。插入语用逗号或括号；只有真正需要停顿强调时才用，一页里越少越好。

## 读者与节奏

- 第 1–5 章面向有游戏经验、没有编程基础的读者：首次出现的文件、目录和注册操作写清位置与改法，代码片段可以带解释性行注释。
- 第 6 章起假定读者会基本 Java 语法和构建，重点讲游戏对象、调用时机、数据流和生效条件。
- 同类操作再次出现时指明沿用哪一节的做法，只讲新增差异。
- 机制讲解交代谁提供数据、谁读取、何时生效、在哪里看到效果。
- 示例的数值和资源选择说明设计理由，深度符合当前任务，不为凑篇幅展开无关字段。

## 依赖库

- 原版章节首次用到依赖库时，只简短说明用途、添加方式和当前用法，详细讲解留给依赖库章节，并用 `[C数字-S数字]` 指向它。
- 依赖库章节以 "这个库替您省掉了什么" 组织，片段围绕实际需求，不逐个罗列方法。

## 页面外框

### 章页

- 章页由 H1、介绍和 `## 本章各节` 下的自动列表组成，介绍段数不限。
- 介绍只写概览、引导、观念与适用场景，如本章在 MOD 制作中的位置、读者何时会用到它、编者对这类内容的态度；不写文件、字段、对象、命令等技术细节，也不罗列本章将做出的成果。
- 章页介绍是一章的导语，与节导语同一路数，但站位更高、讲的是宏观的事：这一章在整个 MOD 制作里的位置、它接在哪、把读者带到哪里、编者在这一层关心什么。不写具体的文件、字段、类。
- 章页介绍同样先有编者对这类内容的立场，来自本章反复出现的取舍，不写成各章通用的同一套判断，也不以按需求指引阅读的导览句收尾。
- 章页篇幅比节导语长，可以分几段展开，但仍是导语：不预告各节顺序，不复述节的成果清单。
- **章页标题与节页 H1 一律沿用现行标题，不重写、不改动。** 重写章只重写介绍段落。
- 每个章页都在 H1 后写一行 `本章技术基线`，至少写明游戏版本；本章有 Java 或依赖库要求时一并写入，格式见 `.zcode/text-guidelines.md`。

### 节页

- 固定部分：H1、导语、分割线 `---`、阅读时间与操作时间两个斜体段落，随后紧跟 H2；第 6 章起这个 H2 是 `## 前置知识`。
- 每页先有编者对这个题材的立场：想要什么，看不上什么，凭什么这样想。立场必须出自本节正文里编者做过的某个具体取舍，不能凭空设定。导语自然地使用这个立场，不专门把它宣布出来，开头、段数与收法随题材而定，页与页之间不套同一个形状。导语站在动手之前，不预告本节步骤，不复述后文细节与数值，不写本节做完后的状态。风格化的总起句可以单独成段。导语可以点出这一领域的关键接口名，不必刻意回避，但不能变成术语清单；一句之内超过两个反引号片段，就说明它在罗列而不是在说话。
- 正文按制作顺序组织，H2/H3 写动作或对象，如 "设置甲板"、"让系统接受 AI 控制"。
- 每个可运行成果都要在游戏内确认，确认写在成果出现的位置，用一个对应的小标题或段落说明进入方式、操作和应看到的现象，如样本中的 "首舰下水"。
- 可选部分：`## 常见问题` 只收录真实会遇到的报错与症状；`## 建议参考项` 第 6 章起推荐，放在最后。
- 一节的主要成果要带出编者的设计判断：意图、数值或行为的取舍与代价，以及亲自测试后的评价。判断随叙述自然带出，理所当然地写在用到它的地方，不单独成节、不加 "设计取舍" 之类的小标题。次要成果一句带过或不写。
- 不写学习目标、总结或复述本页内容的收尾段落。
- 导语与分割线之间空一行；时间段落紧接分割线，源码写成 `_本节预期阅读时间：\~10 分钟。_` 与 `_本节预期操作时间：\~5 分钟。_`，纯概念页按实际投入填写操作时间。

### 前置知识

- 标题后直接写列表；教程内知识以 `[C数字-S数字]` 开头并说明用到了什么，外部知识直接说明。**条目里只要出现节引用，它必须是该条目的第一个元素**，不能放在句子中间或末尾；节引用之后再写这条知识是什么。
- 只列读者真正需要先完成或先掌握的内容，测试存档、已装 MOD 等环境条件写在游戏内确认处。
- **前置知识只能引用本章之前的内容。** 后续章节才讲的知识，不列进前置知识，也不出现在这里；本节要用到的话，在正文里就地讲清楚。
- 前置知识不限于某一节，也可以是一类知识，如 Java 基础、CSV 规范、JSON 写法。第 1–5 章同样需要前置知识，只有确实没有依赖的页面才可省略。
- 全书通用的规则只在读者第一次实际用到的页面列出，之后的页面不再重复。

### 常见问题

- 每条采用 `- **症状**：原因` 主行，下设缩进 4 空格的 `- **解决方案**：检查位置与修正动作` 子行，条目之间空一行。
- 只写本节操作可能真实触发的问题，原始报错文本保持原样。

### 建议参考项

- 每项采用 ``- `对象`：说明``，交代它与当前任务的关系。
- API 参考写完整包名与类名；`starsector-core` 内的文件写相对该目录的路径，其他位置写从 `Starsector/` 开始的路径。路径约定不在每一项里重复声明。
- 凡是复制过原版文件或改过原版字段的页面，第 1–5 章同样应给出这些原版文件，每一项都须核对其真实存在。

## 引用

- 章节引用用于前置操作、共享 ID、对象来源或机制衔接，并说明当前关系。
- 游戏内确认中的路径、数值、触发条件和应看到的结果写在当前页面，不让读者翻回前文找。
